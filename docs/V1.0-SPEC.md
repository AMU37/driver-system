# مواصفات نظام رحلات السائقين V1.0

## 1. هدف النظام

تسجيل الرحلات التي ينفذها السائقون، ربط كل رحلة بسائق وباص وخط سير، تسجيل الموظفين أثناء الصعود بواسطة الكود، إضافة الموظفين الجدد عند الحاجة، إكمال الرحلة وترحيل بياناتها إلى بيئة Microsoft، واستقبال الرحلات المخططة قبل موعدها بمدة يحددها المشرف.

## 2. حالات الرحلة

```text
planned -> available -> started -> boarding -> completed -> transferred
```

حالات استثنائية:

- `cancelled`
- `needs_review`
- `received`

### قواعد الانتقال

- `planned`: الرحلة مخططة ولكن لم يحل وقت الإتاحة.
- `available`: أصبحت الرحلة متاحة للسائق.
- `started`: بدأ السائق الرحلة.
- `boarding`: تم تسجيل موظف واحد على الأقل.
- `completed`: أكد السائق الوصول وإنهاء الرحلة.
- `transferred`: تم إرسال الرحلة بنجاح إلى Microsoft.

## 3. الصلاحيات

### Driver
- الوصول إلى بيانات حسابه.
- الوصول إلى الرحلات المخصصة له.
- بدء الرحلة المخصصة.
- تسجيل الموظفين في الرحلة.
- إنشاء طلب موظف جديد.
- إكمال الرحلة.
- الترحيل.
- سجل رحلاته وإشعاراته.

### Supervisor
- كل صلاحيات العرض الإشرافي.
- مشاهدة السائقين والباصات.
- إنشاء الرحلات المخططة يدوياً.
- مشاهدة الموظفين.
- مراجعة الموظفين الجدد.

### Admin
- صلاحيات الإدارة الكاملة ضمن V1.0.

## 6. صيغة رقم الرحلة

الافتراضي:

```text
TR-{BUS}-{YYYYMMDD}-{COMPANY}-{SEQ}
```

مثال:

```text
TR-124-20260919-YCSR-001
```

## 7. وقت إتاحة الرحلة

إذا كان وقت الانطلاق `05:30` وعدد الساعات `8`:

```text
Release Time = 21:30 في اليوم السابق
```

## 8. قواعد الموظفين

- البحث الأساسي يكون بالكود.
- الموظف الموجود في قاعدة البيانات يضاف بصورة طبيعية.
- الموظف غير الموجود لا يُنشأ كموظف رئيسي مباشرة، بل يمر بطلب مراجعة.
- لا يسمح بتكرار الموظف نفسه داخل الرحلة نفسها.
- يتم الاحتفاظ بلقطة Snapshot من بيانات الموظف داخل الرحلة حتى تبقى بيانات الرحلة التاريخية ثابتة.
